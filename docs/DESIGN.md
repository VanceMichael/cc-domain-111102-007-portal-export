# 设计决策与风险说明

## 1. 浏览器库选型：Playwright（同步 API）

### 为什么是真实浏览器而不是 HTTP 客户端直连

门户的交互发生在 iframe 内，导出按钮由页面脚本以 `fetch` 异步发起，任务列表
靠局部重绘渲染，下载由浏览器的下载管理器接收。直接用 `urllib`/`requests` 模拟
接口虽然更轻，但会绕过页面真实行为（重绘、iframe 边界、下载事件、401 的页面
表现），而这些正是运营事故的来源。需求也明确要求「在实际浏览器里演示」，因此
选择浏览器自动化，保留门户服务自身行为。

### 为什么是 Playwright 而不是 Selenium

| 维度 | Playwright 1.56 | Selenium 4 |
| --- | --- | --- |
| 下载与响应关联 | `expect_download()` 与响应事件可按页面上下文捕获，能拿到 `X-Export-ID` 响应头 | 下载能力依赖浏览器偏好配置，响应头拦截需要额外的 CDP/日志解析 |
| iframe | `frame_locator` 与普通定位器同构，自动等待 | 需要反复 `switch_to`，重绘后还要重新切换，易持有失效引用 |
| 事件驱动等待 | `expect_response`/`expect_download` 原生协议级等待 | 主要靠隐式/显式等待，更容易退化为固定睡眠 |
| 网络事件 | 响应状态/响应头监听内建，401 可在一处统一捕获 | 需要 performance log 或代理 |
| 资源占用 | 单浏览器 + 单上下文，无头 headless shell 内存占用较低 | 需要 WebDriver 中转进程，链路更长 |

两者都会启动完整浏览器，内存量级相近（单上下文约 200–400MB）；Playwright 省掉
WebDriver 中转进程，且原生事件模型直接消除了「靠睡眠猜时机」的空间。

### 版本固定的原因

受限网络环境无法访问 `cdn.playwright.dev`（实测下载返回 403），浏览器由系统
预置为 chromium-1194，对应 Playwright 1.56.x。因此 `requirements.txt` 固定
`playwright==1.56.0`，避免升级后驱动与浏览器构建号不匹配。

### 资源占用

- 每次运行一个浏览器进程、一个 BrowserContext（等价独立会话）、一个 Page；
  结束时 `context.close() → browser.close() → playwright.stop()` 逐层释放。
- 无头模式使用 headless shell，不创建可见窗口；有头模式仅在人工登录时需要，
  无显示器环境由 Xvfb 提供虚拟显示，Xvfb 本身只占数 MB 共享内存。
- 轮询只发轻量 `/jobs` JSON 请求，间隔默认 700ms（可 `--poll-ms` 调整），
  不加载额外页面；下载文件直接落暂存区，不在内存累积。
- 门户是标准库 `ThreadingHTTPServer`，无第三方服务依赖。

## 2. 误关联风险与防线

同名 `catalogue.csv`、乱序完成、页面重绘是三个独立的错挂来源。归属判断采用
**三重一致**，任何一重不符即拒绝接收：

1. **任务标识（权威键）**：门户为每个任务返回唯一 `job_id`，下载响应带
   `X-Export-ID` 头。采集器要求响应头标识等于账本中的 `job_id`；响应事件
   未捕获时才用带会话的请求补取响应头，绝不凭文件名或点击顺序猜测。
2. **文件内场馆/语言**：CSV 每行含 `venue`、`language` 列，逐行读取并要求
   全文件唯一且与任务参数一致；空文件、截断文件、只有表头、混入第二个场馆
   一律判失败（`app/verify.py`）。
3. **会话世代（epoch）**：每次成功登录递增 epoch 并记录 cookie 值；下载
   证据记录产生它的会话。重新登录后旧 epoch 的下载不被采纳，对账续收的
   任务会显式切换到当前 epoch，从根上避免「旧会话文件挂到新请求」。

下载锚点用 `li[data-job-id='<id>'] a` 按标识即时定位；页面重绘会重建 DOM，
采集器全程只保存定位器（每次使用重新求值），不保存 ElementHandle。

## 3. 异步与重绘：为什么没有固定睡眠

- 提交导出：`expect_response(lambda r: "/export" in r.url)` 等具体响应。
- 任务就绪：轮询循环的推进完全取决于 `/jobs` 返回的 `state`；
  `wait_for_timeout(poll_interval_ms)` 只控制请求频率，不作为完成判据。
- 列表渲染：门户只在加载/提交/点「刷新任务」时重绘，拿到 ready 后点击页面
  自身的刷新按钮并 `expect_response("/jobs")` 等该次重绘的数据，再按
  `data-job-id` 等待下载锚点。
- 接收文件：`expect_download()` 等待浏览器下载事件，而非睡眠后假设文件存在。

## 4. 登录过期与恢复策略

- 统一在响应监听器中识别业务接口的 401，置位 `expired` 事件；任何业务动作
  入口先检查该事件，触发 `SessionExpired`，立即停止导出/下载。
- 恢复方式二选一：
  - **人工登录（默认）**：有头浏览器打开 `/login`，终端提示人工输入演示
    账号、密码与图形验证码，流程轮询到进入 `/workspace` 即继续。验证码
    由人眼识别，采集器不接触答案，不做 OCR、不绕过。
  - **本地演示登录**：仅当门户以 `--test-mode` 启动时，采集器可从
    `/test/captcha/<id>` 读取答案代填。该接口在正常模式返回 404，真实
    门户不存在此通道。
- 恢复后重新走 `reconcile()`：任务在门户侧仍存在就续收（epoch 切换为新
  世代），门户侧确认缺失才标记旧任务失败并重建，避免重复导出。

## 5. 进程退出后的一致性

- 账本 `ledger.json` 每次状态变更后以「临时文件 + `os.replace`」原子落盘；
  事件同时追加到 `events.ndjson`，即使最后一次账本写入前崩溃也有事件流。
- 下载先写 `.staging/<job_id>.part`，校验通过才原子改名为
  `catalogues/catalogue_<venue>_<language>.csv`；失败删除暂存文件、取消
  保留取消态，成品目录永远不会出现半个文件。
- 重跑时 `verified` 请求直接跳过；非终态任务先与门户 `/jobs` 对账：
  命中 → 续收；未命中 → 旧记录留痕（failed）后重建。同一请求的历史记录
  全部保留，`record_for_request` 返回最新一条。

## 6. 只读边界

采集器只触发门户为操作员提供的三个只读能力：提交导出（生成公开目录文件）、
查询任务列表、下载生成结果。不点击预约/支付类控件，不调用任何业务写入接口，
不修改门户状态文件之外的业务数据；门户 `/expire` 仅用于本地演练会话失效。

## 7. 已知限制

- 演示门户任务状态在每次 `/jobs` 轮询时推进计数，轮询频率会影响就绪快慢；
  真实门户若采用服务端推送，可把轮询循环替换为等待推送事件，账本与校验层
  无需改动。
- 人工登录默认超时 5 分钟（`--login-timeout` 可调）；超时后进程退出，
  账本已落盘，再次运行从对账继续。
- 浏览器与 Playwright 版本强绑定，升级需同时验证预置浏览器构建号。
